# Hytale 0.7.2 capability assessment

**Date:** 2026-10-20
**Status:** Accepted — register and adoption order. Not an implementation plan.
**Scope:** Which Hytale 0.7.2 (Update 7 / Chapter I) engine capabilities this project should
adopt, in what order, and behind what boundary.

---

## 1. What this document is

A **register plus an order**. Each capability gets the same fixed fields so entries are
comparable rather than essays, and the document ends in a ranked adoption order.

**It is not an implementation plan.** Each adopted capability gets its own spec and its own
plan. Nothing here authorises code beyond the probes named in §7.

**What prompted it.** The launcher updated to 0.7.2 on 2026-10-20, crossing Update 6 hotfixes
(0.6.6), Chapter I, and the 0.7.2 hotfixes in one jump. Seven compile errors followed, all in
`mod/hytale` probe commands, repaired in `21eb7bf`; four deprecated call sites in the Stormseeker
spine were repaired in `554b9b4`. The repair work surfaced that the engine has grown subsystems
that overlap substantially with `core`, which is what this assessment exists to evaluate.

---

## 2. Method, and four limits on it

Capabilities were identified by listing the 38,436 classes in `HytaleServer.jar`, reading
`javap` signatures, and reading bytecode at real engine call sites. The Update 7 patch notes were
used as a pointer, never as authority — they proved wrong in detail at least once (they name
`ChunkStore.getChunkSectionReferenceAtBlock()`, which is declared one level up on `ChunkGrid`).

Four limits, stated because they bound every claim below:

1. **We cannot tell what is new.** The launcher overwrote the previous jar and no copy survives
   anywhere on disk. Every "new in 0.7.2" attribution in this document comes from the patch notes,
   not from a diff. §7 item 0 exists to stop this recurring.
2. **`@RestrictedApi` is invisible here.** It is Google ErrorProne's annotation; no `com.hypixel`
   class carries it in bytecode. The patch notes say `WorldChunk`/`BlockChunk` accessors are now
   restricted; that cannot be confirmed or enumerated from the jar.
3. **Signatures are hypotheses.** Nothing below has been executed against a running 0.7.2 server.
   Per the project's standing method caution — *"signature inspection is a hypothesis; a probe
   executed on the current build is confirmation"* — every `adopt-now` entry names its probe, and
   the probe runs before any design depends on the capability.
4. **Client-side surface is only partly assessable from here.** `Runestone` and `RunicPanel` do not
   appear in the server jar at all. `Assets.zip` does ship a `Server/Abilities/` asset tree, so the
   ability system has a server-side *asset* surface even though its classes are absent — enough to
   say the `watch` status in §5.8 is conservative, not enough to assess it.

## 3. Governing rules

**The boundary holds, and it earns its keep.** `core` and `quests/stormseeker` contain zero
`com.hypixel` references, enforced by `:core:checkNoPlatformImports` and
`:core:checkNoQuestlineDependency`. When 0.7.2 deleted the entire `World` block facade, the blast
radius was **3 files in 1 module**. That is the property being protected.

**`core` may change; `core` may not import.** The barrier is on dependencies, not on design.
Core's abstractions can be reshaped freely — including redesigned around a better model — so long
as they stay engine-free.

**Every native capability is reached through a port**: an interface defined in `core`, implemented
in `mod/hytale`. The cost is one interface per capability; the benefit is that the next engine
overhaul keeps hitting one module.

**Three rules for the register:**

1. No capability is adopted on signature inspection alone (§2 limit 3).
2. A capability must **displace something or close something open**. "The engine has it" is not a
   reason. This is the YAGNI filter and it is why `gameflags` is not adopted.
3. Ranking is **leverage ÷ risk** — leverage being code deleted plus open problems closed, risk
   being blast radius if the engine concept moves. This is why `points` outranks `encountermanager`
   despite the latter being the larger overlap.

## 4. The storm-bound ore question

Re-opened because the capability set changed. `docs/stormseeker/archive/design.md` §"Storm-Bound
Elemental Ore" specifies ore *visible only during storms*; `docs/stormseeker/archive/quest-phases.md`
records the intended mechanism — place on storm start, and *"on the `onWeatherChanged` event (storm
end), iterate through the map and restore all modified blocks to their original state."*

**Per-player block visibility does not exist.** `BlockPreviewVisibility`
(`AlwaysVisible`/`AlwaysHidden`/`Default`) is builder-tool ghost rendering, not world visibility.
Driving `SetBlockCmd` at individual connections would desync from authoritative server state and is
rejected.

So two mechanisms remain:

| | Block swap | Additive reveal |
|---|---|---|
| Mechanism | `ReplaceBlockTypeEffect`, `randomtick/ChangeIntoBlockProcedure`, `blocktick/ChunkBlockTickSystem` | ore always present; beam/VFX reveal during storms |
| Literal invisibility | yes | no — digging blind still finds it |
| Cleanup / crash safety | tracking map, restart hazard, chunk-unload-mid-storm hazard | nothing to clean up |
| Granularity | world-global | per-observer |

**The deciding argument is new.** Block state is world-global. Player weather is now
*per-player* (§5.1). Block swap matched weather's granularity while weather was world-global; it no
longer does — one player's storm would reveal ore for every player. The same capability that makes
storm-gating better makes block-swap incoherent.

**Decision: additive reveal**, carried by capabilities #1 and #3. The literal-invisibility
property is given up deliberately. If it is later judged essential, that is a *new* decision
requiring a mechanism that does not exist today, not a revival of the block-swap plan.

### MEASURED 2026-10-20 — "per-player block visibility does not exist" is FALSE

> The paragraph above this heading says literal invisibility needs "a mechanism that does not exist
> today." **That mechanism exists and was demonstrated against a live client the same day.** This
> section records the measurement; it does **not** change the decision, which is the operator's.

**`ServerSetBlock` is a `ToClientPacket`** (`com.hypixel.hytale.protocol.packets.world`, plain
`x`/`y`/`z`/`blockId` fields). Written to one player's `PacketHandler` — the same path
`WeatherTracker.sendWeatherIndex` uses — it changes that block **for that player only**, with no
server-side write at all.

**Demonstrated with a same-block control**, because a lone spoofed block cannot be read: the first
attempt used a single crystal spoof and the operator reported *"I don't think the stone block in the
air looked like anything else but stone. The color seemed slightly different, but I'm not sure."*
The probe now places **three `Rock_Stone` blocks in a row** and spoofs only two:

| position | told the client | operator saw |
|---|---|---|
| `x` | nothing — the control | stone |
| `x+2` | `Ore_Gold_Stone` | **gold** |
| `x+4` | `Plant_Crop_Mushroom_Glowing_Orange` | **mushrooms** |

**The server stays authoritative, and that is what makes it safe.** All three were broken by hand
and all three dropped **cobblestone** — `Rock_Stone`'s real drop. So the lie is client-side only: a
spoofed block breaks as, and yields, what the world actually holds. A casual player who digs a
spoofed block gets cobblestone and destroys nothing, which is exactly the property
`canon-alignment-recommendations.md` needs for residue-core protection and which §4's additive
reveal could not provide ("digging blind still finds it").

**One hard constraint, found the expensive way.** The spoof must be sent **after** the engine's own
block update for that position, never in the same tick. `BlockOperations.setBlock` with
`PERFORM_BLOCK_UPDATE` broadcasts a real update, and the first run spoofed in the same tick: the
broadcast won, the operator saw plain stone, and the mechanism was nearly recorded as not working. A
`+2s` re-send fixed it, and the operator's description is the direct evidence — *"for a split second
they were all stone, but the 2 spoofed ones changed very shortly after."*

**A dead end, recorded so it is not retried.** `BlockHarvestUtils.performBlockBreak` does **not**
produce drops when we call it. Three forms, each with a real breaker and a real top-tier pickaxe:

| call | item-entity count |
|---|---|
| 11-arg, **substituted** `BlockType` | 19 → 19 |
| 11-arg, host `BlockType` | 19 → 19 |
| 6-arg, engine reads its own type | 19 → 19 |
| *instrument check* — `ItemUtils.throwItem` | **19 → 20** |

The instrument moving is what makes the three zeros evidence rather than noise. Every hypothesis is
eliminated — not the breaker, not the tool, not the explicit-`BlockType` overload — so drop
production lives further up the interaction path, not in that function. **Drop substitution is
therefore not done via `performBlockBreak`.** The verified route is `BreakBlockEvent` (cancellable)
plus `ItemUtils.throwItem`/`dropItem`, which return a real positioned item entity carrying
`ItemComponent`.

**What this adds to the §4 table** — a third column the original did not have:

| | Block swap | Additive reveal | **Per-player spoof** |
|---|---|---|---|
| Literal invisibility | yes | no | **yes, for the unattuned** |
| Granularity | world-global | per-observer | **per-observer** |
| Cleanup / crash safety | tracking map, restart hazard | nothing to clean up | **nothing — no server state is written** |
| Exploitable | — | — | **no — server stays authoritative** |

**Still unmeasured, and it decides the re-send policy:** whether a spoof survives a chunk reload,
a neighbouring block change, and a relog. The split-second stone flash implies re-send-on-load is
required, with a brief flicker each time — which is a cost `NexusStore` (#2) should be designed
knowing about, since it would occur for every attuned player on every chunk load.

Probe: `/blockspoofprobe`, driven by `scripts/live-probes/drive-blockspoofprobe-client.sh`.

## 5. Capability register

### 5.1 Per-player weather override + effective weather index — **adopt now**

- **What it is.** `WeatherTracker.tryClaimOverride(Ref, int)`, `releaseOverride(Ref)`,
  `setOverrideWeatherIndex(int)`, `clearOverrideWeatherIndex()`,
  `resolveUnoverriddenWeatherIndex(...)`; and `WeatherResource.getEffectiveWeatherIndex(int)`.
- **Verified.** All signatures present. `getEffectiveWeatherIndex` bytecode reads:
  `forced = getForcedWeatherIndex(); if (forced != 0) return forced; return
  getWeatherIndexForEnvironment(env);`
- **The asymmetry worth keeping.** `WeatherTriggerCondition.isConditionMet` calls
  `getWeatherIndexForEnvironment`, **not** `getEffectiveWeatherIndex`. So the documented trap —
  forcing weather starves the environment map the condition reads, making `/weather set` useless for
  testing — **survives in native objectives** while a correct path now exists for our own code.
  This is a direct argument for keeping weather gating in our own ports rather than delegating it to
  native objective conditions.
- **What we hand-roll.** `HytaleWeatherReader` reads `WeatherTracker.getWeatherIndex()`. That stays
  correct; the override and effective-index surface is additive.
- **Port shape.** `WeatherGate` (read: is this player in weather W) and `PlayerWeatherController`
  (claim/release an override), both in `core`, implemented in `mod/hytale`.
- **Deletes.** Nothing yet. Unblocks §4 and encounter-scoped storms.
- **Costs.** Claim/release is cooperative; two systems claiming the same player must agree on
  precedence. The port must make ownership explicit rather than hiding it.
- **PROBED 2026-10-20 — passes on every question, 23/23 assertions.** `/weatheroverrideprobe` was
  written and run against a live 0.7.2 server with a client attached, once unforced and once with
  `/weather set Zone1_Rain` applied. Baseline `59 (Zone1_Cloudy_Medium)` / forced
  `54 (Zone1_Rain)`, overrides claimed to `1 (Zone4_Wastes_Rain_Heavy)` and `2 (Zone4_Wastes_Rain)`.

  - **Precedence is `per-player override > world-forced > environment`**, measured. The override beat
    the force, and release fell back to the **force** rather than the environment. This is the result
    §4 depends on: a player can be storm-gated while the world is not, and `/weather set` can no
    longer mask a per-player gate.
  - **Claim, release and refusal all behave.** The claim takes; release restores; a *different*
    claimant is refused while the owner is valid; a foreign `releaseOverride` is refused.
  - **A stale owner cannot strand an override.** The incumbent blocks only while `isValid()`, and
    `updateWeather` calls `clearOverrideWeatherIndex()` outright on an invalid owner — so a
    disconnect self-heals. A valid claimant takes over from an invalid incumbent.
  - **Ownership is reference identity (`if_acmpeq`), and `PlayerRef.getReference()` returns a cached
    field** — measured as the same instance across calls. So the port may re-derive the claimant Ref
    rather than storing it. Any *other* source of a `Ref` to the same entity would not match.

- **Three corrections this probe forces on the text above.**

  1. **"A second claim while held is refused" is wrong for the same claimant.** The identity check
     jumps *into* the assignment, so a same-claimant re-claim **succeeds as an update**. Measured:
     returned `true` and replaced the index. Refusal applies only to a *different* claimant. A probe
     that tested only the spec's wording would have passed and still described the mechanism wrongly.
  2. **The claim protocol is advisory, which the "Costs" bullet understates.**
     `setOverrideWeatherIndex(int)` and `clearOverrideWeatherIndex()` are public and perform **no
     ownership check at all** — measured: an unclaimed caller set an override, and a non-owner
     cleared one. "The port must make ownership explicit" is therefore not enough; the port must
     **not expose those two methods**, or ownership means nothing.
  3. **Index 0 is a sentinel, not a weather.** The gate is `overrideWeatherIndex != 0` and
     `releaseOverride` clears to 0, so `tryClaimOverride(ref, 0)` returns **true and does nothing**.
     There is no way to override a player *to* index 0. A port accepting 0 from a caller would
     silently no-op; it must reject it.

- **One trap worth carrying to the port.** `getWeatherIndex()` is a **send-log, not a resolver** — it
  returns the last value actually sent to the client. Claiming an override and immediately reading it
  back returns the *pre-claim* value, and the probe asserts that stale read deliberately as a
  control. `WEATHER_UPDATE_RATE_S` is 1.0s and `WeatherSystem$TickingSystem` normally drives the
  update, so the probe calls `tracker.updateWeather(...)` itself: a command that slept waiting for
  that tick would be blocking the thread the tick runs on. `WeatherGate`'s read side should use
  `resolveUnoverriddenWeatherIndex` / `getEffectiveWeatherIndex`, never `getWeatherIndex()`.

- **Probe shape, and why it is not an extension of `/weatherprobe`.** This bullet originally read
  "Extend `/weatherprobe`". It was written before the mechanism was read, and the two probes are
  opposites: `WeatherConditionProbeCommand` is a pure read whose value is reproducing
  `WeatherTriggerCondition`'s own path, and it is an `AbstractWorldCommand` *on purpose* so it runs
  console-only with no client. The override probe **mutates** per-player state and cannot answer
  anything without a connected player. It shipped as a separate `/weatheroverrideprobe`.
  It also declines to force weather itself — forcing starves the `environmentWeather` refresh, which
  `compareAndSwapHour` then gates for up to an in-game hour — so test 10 runs only when the operator
  has already forced weather.

### 5.2 `builtin/points` spatial index — **adopt now**

- **What it is.** `PointManager`, `PointSpatialIndex`, `PointEntry`, `PointCodecs`,
  `PointSnapshot`, `PointPrefabContributor`, `PointToolPacketHandler`, `ui/PointInspectorPage`.
- **What we hand-roll.** *Nothing yet* — and that is the point. N9's next implementation item is
  `ResidueField`, a world-level owner of the nexus set, which needs exactly a persisted, queryable
  spatial point store. This is adopt-before-build; the leverage is code never written.
- **Port shape.** `NexusStore` in `core` — `add`, `remove`, `within(centre, radius)` — implemented
  over `PointManager` in `mod/hytale`. Core keeps owning what a nexus *is*.
- **Deletes.** Pre-empts a hand-rolled spatial index and its persistence.
- **Costs.** Couples nexus persistence to an engine subsystem whose codec may change. Mitigated
  by the port: core's `NexusStore` contract is ours.
- **PROBED 2026-10-20 — passes on every question.** `/pointprobe` was written and run across two
  boot cycles against a live server. Cycle 1 registered five points at known distances along +x;
  cycle 2 reported what survived before registering anything.

  - **Persistence: 5 of 5 survived the restart, tags intact.** Serialized to
    `universe/worlds/<world>/resources/PointData.json`, with a `.bak` sibling, holding position,
    name, enabled flag and tags.
  - **Query correctness: exact.** `queryRadius(origin, 20)` returned precisely
    `[probe_5, probe_15]` — the 25 m point correctly excluded, so it is sphere semantics and not a
    bounding box. `queryRadius(50)` → all 5; `queryRadius(1)` → 0. The expected set was stated in
    the probe's own output rather than only its count, because a count cannot catch an off-by-one.
  - **Scope: world, confirmed twice** — `PointEntry.worldName`, `PointsPlugin.getManagerForWorld`,
    and a per-world file on disk.
  - **The index is a `KDTree`** (`PointSpatialIndex.tree`) with a lazy `rebuildIfDirty`, so radius
    queries are O(log n + k) rather than a linear scan. That settles the scale question for N9.
    It also dictates the usage pattern: **bulk-register, then `markSpatialDirty()` once** — not
    register-and-rebuild per point, which would be O(n² log n) over a convergence.

- **One design constraint found by probing.** The tag-filtered overload
  `queryRadius(pos, r, String)` matches on the tag **key**, not `key:value` — measured, since
  `"legendary_element"` returned 5 and `"legendary_element:lightning"` returned 0. So N9's
  element-pair typing must put the discriminator in the **key** (a key per pair), not in the value.
  That is cheap, but it is the opposite of the obvious modelling and would have been found late.

### 5.3 `builtin/beam` — **adopt now, probe first**

- **What it is.** `AttachedBeam`, `BeamComponent`, `BeamSystems`, `asset/Beam`,
  `asset/BeamPacketGenerator`, `interaction/AttachBeamInteraction`, `command/BeamCommand`.
- **What we hand-roll.** Residue expression is particle-only today
  (`ResidueParticleProbeCommand` via `ParticleUtil.spawnParticleEffect`).
- **Port shape.** `CurrentRenderer` in `core` — "express a current between A and B", "reveal a
  nexus at P" — implemented over beams in `mod/hytale`.
- **Deletes.** Nothing immediately; it is the expression mechanism §4 depends on.
- **PROBED 2026-10-20 — the gating question is answered YES.** `/beamprobe` was written, deployed
  to a live 0.7.2 server and executed headless. The anchor-entity-per-endpoint fear was **wrong**:

  - Four beam assets ship and resolve — `Basic`→3, `Chain`→2, `Fire`→1, `Rope`→0
    (`Server/Entity/Beams/*.json` in `Assets.zip`).
  - `AttachedBeam.toPosition(...)` and `toBlock(...)` construct and report `isValid()` true.
    Beams are **not** entity-only; the far end costs nothing.
  - One holder carried 4 beams in a single spawn, and `MAX_BEAMS` is **64**. So a nexus with N
    outgoing currents costs **one** holder entity, not N and not N+1.

  Positional expression is therefore cheap, and §4's additive-reveal decision stands on measured
  ground rather than inference.

- **One unresolved result, and it is not the gating one.** `BeamComponent.spawn` returned a valid
  holder at one test position and **null** at another, deterministically across three runs. A 2x2
  isolated it: beam count is irrelevant, position is the sole determinant.

  | | z = +0.5 (force-loaded chunk) | z = −3.5 (chunk the server warns is unloaded) |
  |---|---|---|
  | 1 beam | null | VALID |
  | 4 beams | null | VALID |

  The direction is inverted from the naive expectation — the *loaded* chunk fails. The mechanism is
  **not** explained by `Store.addEntity`, whose only null return fires when its 4th `parentRef`
  argument is non-null-but-invalid; `spawn` calls the 2-arg overload, which passes `parentRef` null,
  so that path cannot fire. No mechanism is asserted here.

  **Treat this as probably a headless artifact until re-run with a client attached.** Entity
  spawning is bound up with chunk tracking, which is driven by connected players, and this run had
  none. That makes the headless result the suspect half, not the engine.

- **Next probe.** Re-run `/beamprobe` with a client connected, which also supplies the one thing a
  headless run can never give: confirmation that the beams actually *render*. A `holder VALID` with
  nothing drawn is a different failure, and the probe says so in its own output.

### 5.4 World map markers / `DiscoverableMapMarkers` — **adopt when #1–#3 land**

- **What it is.** `MapMarkerBuilder`, `DiscoverableMapMarkers`, `POIMarkerProvider`,
  `MapMarkerAlert`, `WorldMarkersResource`, `UserMapMarkersStore`, `MapMarkerUtils`; markers support
  an `IconSize` of `Default` or `Major`.
- **What it closes.** N10 "wild availability", which the 2026-08-30 session close records as
  explicitly **not solved** by N9: the nexus-density gain decays with distance (8.2x at 0–200 m,
  1.4x at 1–2 km). That is substantially a *discovery* problem, and discovery is what markers do.
- **Port shape.** `DiscoveryPublisher` in `core` — "this feature at P has become known to player X".
- **Costs.** Markers are a player-facing surface with its own asset schema; a design mistake here is
  visible to every player. Also risks making residue feel like a checklist rather than something
  found, which is a design judgement for the operator, not a technical one.
- **Probe.** Publish a marker programmatically at a known position and confirm it appears, and that
  `DiscoverableMapMarkers` can gate it on discovery rather than showing it from world start.

### 5.5 `triggervolumes` → arena bounds and invariants — **adopt later, high blast radius**

- **What it is.** 240 classes. Rules: `NoBuildRule`, `NoDamageRule`, `NoDestroyRule`,
  `NoHarvestRule`, `NoHealRule`, `NoTickRule`, `NoUseRule`, `NoDoorOpenRule`, `FlyRule`,
  `DamageMultiplierRule`, `CreativePlacementRule`. Conditions: `PlayerCountCondition`,
  `EntityCountCondition`, `CooldownCondition`, `ItemCondition`, `GameModeCondition`,
  `PermissionCondition`, `BlockTypeCondition`, `RandomChanceCondition`. Effects include
  `ModifyRulesEffect`, `RemoveEntitiesEffect`, `ClearRespawnPointsEffect`, `GiveItemEffect`,
  `PastePrefabEffect`, `DamageEntityEffect`.
- **What we hand-roll.** `ArenaBounds`, `ArenaInvariant`, `ArenaInvariantRegistry`,
  `ArenaInvariantBridge`, `BoundsInvariant`, `ArenaRevocationController`, `ArenaRevocationTracker`,
  `ArenaBoundsViolatedEvent`, `ArenaPhase`, plus `internal/legendary/arena/geom`.
- **Deletes.** The largest single deletion available in `core` — roughly the whole arena package.
- **Why it is ranked low despite that.** It is `core`'s live encounter subsystem. Items 1–4 are
  additive or greenfield; this one replaces something working. It should follow them, and it needs
  its own spec with a migration path, not a flag day.
- **Costs.** Trigger volumes are asset-authored. Moving invariants into assets moves them out of
  code review and out of the test suite — an invariant that today is pinned by a unit test would
  become a JSON file. That trade needs deciding explicitly, not absorbing silently.
- **Probe.** Define one volume with `NoBuildRule` + `PlayerCountCondition`, verify enforcement, and
  verify what happens on server restart mid-encounter.

### 5.6 `builtin/instances` → encounter instancing, exit, return — **adopt later**

- **What it is.** `InstancesPlugin`, `InstanceValidator`, `config/InstanceDiscoveryConfig`,
  `config/InstanceWorldConfig`, `config/WorldReturnPoint`, `config/ExitInstance`,
  `event/DiscoverInstanceEvent`, `event/EnterInstanceTeleporterEvent`, instance commands,
  `blocks/InstanceBlock`.
- **What we hand-roll.** `EncounterInstance`, `internal/legendary/instance`,
  `api/legendary/access`, `api/legendary/exit`.
- **Why later.** `docs/architecture/native-objectives-migration-cost.md` already documents the risk
  concentration here — visibility mode (`WORLD_VISIBLE` / `INSTANCE_VISIBLE`) and loot rights — and
  flags it as "the part most at risk of being misread as replaced". That analysis stands and applies.
- **Probe.** Deferred until this is scheduled.

### 5.7 `builtin/encountermanager` — **adopt opportunistically, after #1 and #5**

- **What it is.** `EncounterManager`, `EncounterMembers`, `EncounterMemberCollector`,
  `EncounterBossBarState`, `EncounterAudioState`, **`EncounterWeatherState`**, plus NPC actions
  (`ActionSetEncounterWeather`, `ActionSetEncounterBossBar`, `ActionGrantReward`,
  `ActionStartEncounterMusic`, `ActionSignalWorldEvent`).
- **Assessment.** Overlap is **partial and mostly presentational**. Our encounter framework owns
  lifecycle, join/reuse policy, activation sessions and arena invariants; the engine's owns members,
  boss bars, encounter-scoped audio and weather, and reward granting. These are complementary more
  than competing.
- **The pointed piece.** `EncounterWeatherState` is encounter-scoped weather, which lands directly
  on Stormseeker's theme and should be evaluated together with #1 rather than separately.
- **Costs.** It is NPC-action and asset-builder driven, which suits boss encounters and may not suit
  a trial with no NPC antagonist.

### 5.9 Rejected, with reasons

Recorded so they are not re-checked:

- **`builtin/reactiveblocks`** — explosives only (`BlockExplosive`, `ExplosiveSystems`). The name
  suggests general block reactivity; it is not that.
- **`builtin/augmentblocks`** — block upgrade/progression UI.
- **`builtin/landiscovery`** — LAN *server* discovery (`LANDiscoveryThread`). Networking, not
  gameplay discovery. The name is the trap.
- **`builtin/rewards`** — `EntitlementReward` / `RewardAsset`; account entitlements, not in-game
  rewards. Does not overlap `api/legendary/reward`.

## 7. Drift posture

**Item 0 — the API-surface baseline.** This session could not answer "what changed" because the
launcher overwrote the only copy of the previous jar. Commit a generated snapshot of the engine's
public API surface (class list plus `javap` signatures for the packages this project touches) so the
next update is a diff rather than an archaeology exercise. Cheap, and it converts
`Hytale: API drift`'s binary verdict — *does our code still compile* — into an answerable *what
moved*.

**Deprecations.** `PlayerRef.getComponent(ComponentType)` and `PlayerRef.replaceHolder(Holder)` are
deprecated. Both call sites of the former in this project were migrated in `554b9b4`;
`replaceHolder` is not used here. Neither carries `forRemoval`.

**What to watch.** Anything reached through `World` — 0.7.2 narrowed it to lifecycle, entities,
stores and scheduling, and that narrowing looks deliberate and ongoing. Anything still routed
through `BlockChunk` or `WorldChunk`, which the patch notes mark restricted even though the
annotation is invisible to us.

**Deferral #18 has fired.** `/worldgen2` exists in `builtin/hytalegenerator/commands` with `create`
(alias `editor`), `concurrency`, and a `ViewportCommand`; `CubicTestWorldGenProvider` is present.
The trigger was worded *"`/worldgen` gains a world-creation subcommand"* — what shipped is a
separate command carrying `create`, so the predicted surface differs while the end state the trigger
pointed at has arrived. Core `/worldgen` still has only `reload` and `benchmark`. The deferral's
second trigger — a boot logging a generator other than `HytaleWorldGenProvider{name='Default'}` —
remains unchecked and needs a server boot.
